## 1. 密码学套件（基线，禁止自研密码学）

| 用途 | 算法 | 实现 |
| --- | --- | --- |
| 身份签名 | Ed25519 | @noble/curves |
| DH / 密钥协商 | X25519 | @noble/curves |
| KDF | HKDF-SHA-256（RFC 5869） | @noble/hashes |
| AEAD | XChaCha20-Poly1305（24B 随机 nonce） | @noble/ciphers |
| 内容哈希 / 指纹 | BLAKE3（32B 输出） | @noble/hashes |
| 文本编码 | base58btc（DID/伪地址）、小写 hex（JSON 序列化） | @scure/base |

X25519 私钥在生成与持久化时**必须 clamp 规范化**（`k[0]&=248; k[31]&=127; k[31]|=64`，RFC 7748 §5）——消除等价类，使存储完整性校验可覆盖私钥每一字节。

## 2. 身份与 DID

- 分层密钥：`IK-ed`（Ed25519，DID 本体）+ `IK-x`（X25519，X3DH 身份 DH 密钥）+ `DK-ed`（设备签名，M0 单设备）。
- `DID = "did:mychat:" || base58(IK-ed 公钥)`。自认证，无需注册机构。
- `IK-x 绑定`：`ikxBindingSig = Ed25519.Sign(IK-ed, "mychat:ikx-bind:" || IK-x 公钥)`。所有采信 IK-x 公钥的场景必须先验该绑定（防中间人替换）。
- 身份序列化（本地持久化）必须具备全字节防篡改校验：did 重算一致 + 三对密钥公私钥一致 + IK-x 绑定验签 + X25519 私钥 clamp 规范性。

## 3. 用户名记录（Registry）

```
UserNameRecord = { name, did, ktIndex, signature }
被签消息 = "mychat:name-v1:" || u16be(len(name)) || name-utf8 || did-utf8 || u64be(ktIndex)
signature = Ed25519.Sign(IK-ed, 被消息)
```

- 客户端**永远**自主验签后才采信映射（SR-5）；节点验签仅作垃圾准入。
- 用户名约束（v0.1）：`^[A-Za-z0-9_-]{1,64}$`。
- 每次注册必须锚定 KT 日志事件（type=`register`，payload=name-utf8）。

## 4. 预密钥束（PreKeyBundle）

```
PreKeyBundle = { did, ikxPublic(32B), ikxSignature, spkPublic(32B), spkSignature, spkExpiresAt, opkId, opkPublic(32B) }
spkSignature  = Ed25519.Sign(IK-ed, "mychat:spk:" || spkPublic)
ikxSignature  = 同 §2 绑定签名
opkId         = u32be(BLAKE3(opkPublic)[0:4])      // OPK 公钥指纹（防 OPK 篡改）
spkExpiresAt  = 毫秒 epoch（v0.1 有效期 ≤ 30 天）
```

- 二进制编码（251B 定长，v1）：`"MCPB" magic(4B) || version(1B=1)` + 6 个 `u16be 长度前缀` 字段（did 变长，其余定长）+ `spkExpiresAt(u64be)` + `opkId(u32be)`。解码端严格校验 magic/版本/各长度/总长/did 格式。
- 节点分发端点对 bundle 验签后仅按 DID 存"当前版本"；客户端仍须自主验签。

## 5. X3DH 握手（1:1 会话建立）

发起方 A → 响应方 B（B 的 bundle 已验证）：

```
EK_A        = 一次性 X25519 密钥对
DH1 = X25519(IK-x_A, SPK_B)   DH2 = X25519(EK_A, IK-x_B)
DH3 = X25519(EK_A, SPK_B)     DH4 = X25519(EK_A, OPK_B)
SK  = HKDF-SHA256(ikm = 0x00(32B) || DH1||DH2||DH3||DH4, salt = 0x00(32B), info = "mychat:x3dh:v1", 32B)
AD  = IK-x_A 公钥 || IK-x_B 公钥
```

- 初始消息头：`{ ikxSenderPublic, ekPublic, opkId }`（响应方据此定位 OPK；**响应方必须在接受后销毁该 OPK**）。
- 响应方镜像四组 DH 得同一 SK；SK 即 Double Ratchet 初始 root key 输入。
- 握手首条消息明文（Inner Handshake Payload，JSON UTF-8）：`{ "v": 1, "fromDid": string, "fromName": string|null, "note": string }`。

## 6. Double Ratchet（会话加密）

Signal 规范实现（`packages/core/src/signal/ratchet.ts`），要点：

- `KDF_RK(rk, dh) = HKDF(rk||dh, salt=rk, info="mychat:dr:rk:v1", 64B) → (rk', ck)`
- `KDF_CK(ck)   = HKDF(ck, salt=0x00(32B), info="mychat:dr:ck:v1", 64B) → (ck', mk)`
- 消息头 `DrHeader = { dh(32B), pn(u32be), n(u32be) }`，明文传输且并入 AEAD 关联数据：`AD_total = AD || header || nonce`。
- 每消息独立 `mk` + 24B 随机 nonce；跳过消息上限 `MAX_SKIP = 1000`；跳过 key 保存至乱序消费。
- **重放防护**：当前链内 `n < recvCount` 的消息直接拒绝（不推进链）；skipped 中 key 消费即删（第二次必败）。
- 传输格式见 §7。

## 7. 会话消息传输格式（信封 payload 内层）

**撤回声明（v0.2 增补，S16）**：内容载荷（chat/image/file）携带可选 `mid`（发送方消息 id，发送方命名空间内唯一）；发送方撤回时发 `{v:1, type:"recall", ids:[mid...]}`，接收方按 `remoteId`（= 收到的 mid）匹配标记本地占位"此消息已撤回"（内容清除）。mid 不参与加解密，仅在密文内层。

```
kind = 0x01 初始消息:
  [0x01][ikxSender(32B)][ekPublic(32B)][opkId(u32be)][DrHeader(40B)][nonce(24B)][ctLen(u32be)][ct]
kind = 0x02 后续消息:
  [0x02][DrHeader(40B)][nonce(24B)][ctLen(u32be)][ct]
DrHeader = [dh(32B)][pn(u32be)][n(u32be)]
```

## 8. 信封与投递（Level0 元数据保护子集）

### 8.1 信封二进制格式

```
[version(1B)=1][epoch(u32be)][padClass(1B)][nonce(24B)][u8be 伪地址字节数][伪地址-utf8][u32be 负载长][负载]
```

- `payload = applyPadding(内层 wire)`：`[u32be 原长][wire][零填充]` 至档位定长。
- 填充四档：`256B / 1KB / 16KB / 128KB`（`padClass 0..3`，按 `wire.length+4 ≤ 档位` 选最小档）。

### 8.2 伪地址与会话信箱

```
mailboxSecret = HKDF(SK, salt=0x00(32B), info="mychat:mailbox-secret:v1", 32B)
epoch = floor(unix_ms / EPOCH_MS)，EPOCH_MS = 60_000
信箱伪地址 = base58(HKDF(mailboxSecret, salt=u64be(epoch), info="mychat:mailbox:v1:i2r"|"r2i", 18B))
方向：senderIsInitiator === sending → "i2r"，否则 "r2i"（双方视角计算结果一致）
```

伪地址每会话每 epoch 轮换；中继/存储只见伪地址（SR-2）。

### 8.3 发现信箱（新会话可达性）

```
discoveryInboxId = base58(HKDF(IK-ed 公钥, salt=0x00(32B), info="mychat:discovery:v1", 18B))
```

承载握手初始消息。**边界披露（Level0）**：发现信箱地址可被关联到 DID；会话流量不受影响。匿名化握手为 M2 增强项。

### 8.4 投递模型

- **信箱为主通道**（可靠、最终一致 NFR-5）：所有消息 append 至目标信箱，接收端按单调 cursor 增量拉取；拉取窗口须覆盖 `[now-1, now, now+1]` 三个 epoch 防轮换漏收。
- **WS 仅作唤醒**（加速）：`mailbox-activity` 通知不含内容；客户端收到后走统一拉取路径（天然去重）。
- 在线直投（`IRelay.send`）为协议保留边界，v0.1 客户端不依赖。

## 9. 节点接口（dev-node v0.1）

| 方法/路径 | 说明 |
| --- | --- |
| `POST /v0/registry/register` | 注册 `{ record }`；节点验签+重名检查 |
| `GET /v0/registry/resolve/:name` | 查询记录（404 = 不存在） |
| `PUT /v0/registry/bundle/:did` | 上传 bundle（节点验签 + DID 格式校验） |
| `GET /v0/registry/bundle/:did` | 取 bundle（404 = 不存在） |
| `POST /v0/kt/append` · `GET /v0/kt/list/:did` | KT 事件 v0（append-only） |
| `PUT/GET /v0/storage/blocks/:cid` | 加密块（CAS 幂等，≤16MB） |
| `POST /v0/storage/mailboxes/:id/append` | 投递信封（结构校验：nonce 24B、padClass 0-3、payload ≤128KB；配额 1000 条） |
| `GET /v0/storage/mailboxes/:id?cursor=N` | 增量拉取 `{ envelopes, cursor }` |
| `POST /v0/relay/send` | 在线直投（202 = 已尝试投递） |
| `WS /v0/relay/subscribe?mailbox=:id` | 唤醒订阅（`mailbox-activity` / `envelope` 直投） |

### 9.5 唤醒网关（M1 定稿，FR-5.6 的 Level0 形态）

- **语义**：网关只承载"某伪地址信箱有新内容"的布尔信号（`mailbox-activity`），**永不承载内容**——内容一律走信箱拉取路径（§8.4）。
- **信号可关联性边界（Level0 如实披露）**：WS 长连接的 IP/时序可被网关观察者关联到伪地址（伪地址每 epoch 轮换缓解跨期关联）；信号与 DID 的最终解耦（sealed sender 化网关、真实 Web Push/VAPID 令牌池与轮换）为 M2。
- **浏览器通知（M1）**：客户端在页面隐藏时以 Notification API 呈现摘要（内容不出本机）；页面关闭即无通知通道（W2），推送网关的常驻形态 M2。

线格式：信封二进制字段 base64 的 JSON。节点可信边界：只搬运密文、只做结构与签名准入（见产品设计报告 §2.3）。

**多信箱单连接订阅（v0.2）**：`WS /v0/relay/subscribe?mailboxes=:id1,:id2,...`（逗号分隔，≤64 个，单信箱参数 `mailbox=` 保留兼容）——浏览器同 host 连接上限（6）下，多会话场景每信箱一条 WS 会耗尽连接池导致后续 HTTP 挂起（v0.1 形态的真实缺陷）；唤醒信号带 `mailboxId` 字段标识来源信箱。

### 9.6 设备注册表与按设备分发（M2-S10 定稿，FR-1.4）

**设备凭证（Device Certificate，DK cert）**：IK(Ed25519) 签名，覆盖确定性编码
`"mychat:device-cert-v1:" || len(did)||did || len(dkId)||dkId || len(label)||label || issuedAt(8B) || expiresAt(8B)`。
`dkId = base58(DK-ed 公钥)`，`label` 为设备描述，默认有效期 90 天（临期 7 天客户端自动续签 = 同 dkId 重登记）。

**吊销声明（Device Revocation）**：IK 签名 `"mychat:device-revoke-v1:" || len(did)||did || len(dkId)||dkId || revokedAt(8B)`。

**节点端点**：

| 方法/路径 | 说明 |
| --- | --- |
| `PUT /v0/registry/devices/:did` | 登记凭证（验签准入）→ 锚定 KT `device-add` |
| `DELETE /v0/registry/devices/:did/:dkId` | 吊销（验签 + 幂等）→ 删除该设备 bundle/OPK 池 + 锚定 KT `device-revoke` |
| `GET /v0/registry/devices/:did` | 设备列表（节点视图；**客户端只作展示，采信须本地折叠 KT 事件流验签**，SR-5） |

**按设备分槽分发**：bundle 模板与 OPK 池均按 `(did, dkId)` 存储；`PUT/POST/DELETE .../bundle/:did[...]?device=dkId` 须指向有效设备（已登记、未吊销、未过期，403 = 失效）。`GET /v0/registry/bundle/:did` 在有效设备集内**确定性 round-robin** 轮询（多设备自然负载均衡）；无有效设备 → 404。

**对端会话轮换**：联系人不被推送吊销事件；客户端在发送路径节流核对（每联系人 ≥60s 一次）——拉取对方 KT 事件流 → 本地 `foldDeviceEvents` 折叠（逐事件验签）→ 有效设备集指纹（blake3 of 排序 dkId 列表）与会话建档时不一致 → 自动重新握手（S9 会话替换语义，历史保留，UI 轻提示）。

**边界（如实披露）**：
- 当前 Web 客户端每台设备持有 IK 私钥副本（Level0）；DK 凭证承载设备生命周期与联系人核验，"DK 作为实际加密操作者（SPK 由 DK 签名、IK 不落端）"需 bundle wire v2（§4 不升版），属后续里程碑。
- 会话绑定创建它的握手：多设备不自动互相同步会话历史（各设备各自握手）；吊销只保证被吊销设备不再获得新 OPK——其已建立的旧会话的历史消息仍在其本地（设备失窃的被动泄露窗口与 Signal 一致，依赖消息历史保留策略缓解）。
- 被吊销设备再上传材料被拒（403）；伪造吊销（非 IK 签名）被拒（400）。

### 9.7 Web Push 离线唤醒（M4-S15，W2 补全）

| 方法/路径 | 说明 |
| --- | --- |
| `GET /v0/push/vapid` | 节点 VAPID 公钥（base64url；订阅 applicationServerKey） |
| `PUT /v0/push/subscribe` | 登记/更新订阅 `{ subscription, mailboxes[] }`（整体覆盖，≤256） |
| `DELETE /v0/push/subscribe?endpoint=` | 注销 |

- **无 payload push**：节点经浏览器推送服务发送空消息体（仅 VAPID 签名）——推送服务与节点都接触不到内容或语义信息；SW 展示本地静态文案。
- **VAPID 密钥**：持久化到数据目录（订阅的 applicationServerKey 必须与发送私钥匹配）；纯内存模式每次重启重新生成（旧订阅失效——开发属性）。
- **触发**：信箱 append 即对该信箱关联订阅 fire-and-forget 投递；410/404 自动移除订阅。推送失败不影响投递主路径。
- **边界**：Chrome/Edge 需 HTTPS 或 localhost；iOS Safari 需 PWA 安装；浏览器到真实推送服务的端到端链路属手动验收。

## 10. 安全考量与边界（v0.1 如实披露）

| 项 | 状态 |
| --- | --- |
| 内容机密性（SR-1） | 全程 E2EE；节点无明文路径 |
| 关系机密性（SR-2） | 会话流量伪地址轮换；**发现信箱与 DID 可关联**（§8.3），时序分析抗性有限（Level0） |
| 重放/篡改/伪造（SR-4） | AEAD + header 绑定 + 链内重放拒绝 + skipped 消费即删 |
| 映射可验证（SR-5） | 双端验签 + KT v0（append-only）；Merkle 证明 M1 |
| Web 端密钥存储（W1） | IndexedDB 无系统级保护；口令加密与社交恢复 M1 |
| OPK 单发 | M0 单 OPK：并发握手可能失败（后到者拒），重新添加即可；OPK 池 M2-S9 |
| 设备吊销（FR-1.4，事后泄露止损） | M2-S10：吊销即停发新 OPK + 对端自动轮换；被吊销设备本地历史不远程擦除（见 §9.6 边界） |
| 群组前向隔离/断读（FR-6.1/6.2） | M3：入群 epoch+1（new-only）、移除/退群 epoch+1 双面失效（信箱轮换 + SK 重分发）；Sender-Keys 过渡形态边界见 §12.5 |
| 动态条目作者性 | 加固②：日志条目 IK 签名，圈密钥持有者伪造他人条目在验签处被拒；momentKey 可重置（不自动轮换） |

## 12. 群组协议（v0.2，FR-6.1/6.2，Sender-Keys 过渡形态）

### 12.1 群状态（GroupState）

`{ v:1, groupId, name, owner, epoch, members[], signature }`：

- `groupId = base58(random 32B)`（不绑定创建者 DID）；`epoch` 从 1 起单调递增。
- `members[]`：`{ did, role: "owner"|"member", joinedEpoch }`，**按 did 排序为规范化序**；上限 50（v1 硬编码）。
- **签名**：owner IK(Ed25519) 覆盖确定性编码
  `"mychat:group-state-v1:" || len(groupId)||groupId || len(name)||name || len(owner)||owner || epoch(4B) || memberCount(2B) || Σ(len(did)||did || role(1B) || joinedEpoch(4B))`。
- **验签锚点**：常规状态以 `state.owner` 公钥锚定；**权威转让态**（签名出自原 owner）由持有上一状态的验证方以 `verifyGroupState(state, prevState)` 路径验证（同群、epoch 连续 +1、原 owner 降级 member、签名出自原 owner）——知情者验证权威转移，不知情者无从验证（这是权威转移的本质）。

### 12.2 状态变更语义（v1 统一：任何状态变更即 epoch+1）

| 变更 | 函数 | 语义 |
| --- | --- | --- |
| 入群 | `addGroupMember` | epoch+1，`joinedEpoch=新 epoch`（**入群即前向隔离**，history: new-only） |
| 移除 | `removeGroupMember` | epoch+1（owner 不可被移除；v1 无转让时的保护） |
| 退群 | 成员发 1:1 消息 `{v:1,type:"group-leave",groupId}` → owner 自动执行移除 | 退群是成员权利；退群者本地同步移除视角 |
| 转让 | `transferGroupOwnership` | epoch+1，旧 owner 降级 member，签名出自原 owner（§12.1 验签路径） |
| 改名 | `renameGroup` | epoch+1（统一语义，编排层复用重分发路径） |

### 12.3 双层加密（Sender-Keys 过渡形态）

**外层**（群信箱密钥，仅当前 epoch 成员可解）：
`信封 payload = nonce(24B) || XChaCha(HKDF(groupSecret,"mailbox-key:"+epoch), nonce, encode(envelope))`

**内层**（每消息独立派生，无链状态无失步）：
`inner = nonce || XChaCha(HKDF(SK[sender],"group-msg:"+groupId:epoch:sender:index), plaintext)`；
`envelope = {v:1, groupId, sender, epoch, index, signature, inner}`，signature = sender IK 覆盖 `"mychat:group-msg-sig-v1:" || groupId || sender || epoch(4B) || index(4B) || inner`。

**防伪造**：被移除者拿不到新 epoch SK，即便持有 groupSecret 构造外层，内层缺 SK 且 IK 验签拒绝。**防重放**：接收端 (sender,index) 单调推进（初始 -1）。

### 12.4 密钥分发（GroupKeysPayload，经 1:1 DR 会话）

`{v:1, groupId, epoch, groupSecret(base58), state(GroupState JSON), senderKeys:[{did,key(base58)}]}`——成员变更时 owner 生成全量新 SK 集（`generateSenderKeys`）并逐一投递幸存成员；接收方本地验签（`applyGroupKeysPayload`，转让态传 prevState）后重建视角。**被移除者不可达**：分发不达 + 群信箱随 epoch 轮换（`HKDF(groupSecret,"mailbox-id:"+epoch)`）。

### 12.5 边界（如实披露）

组内前向保密依赖 epoch 重分发频率，弱于 MLS 树结构；成员变更 O(n)（N≤50）；多设备不互相同步会话历史；群信箱活跃度对节点可见；被移除者已缓存的历史副本不可物理追溯。**>50 人群或更高安全档触发 OpenMLS WASM 立项**（评估报告 §6）。

## 13. 动态协议（v0.2，FR-4.1/4.2/4.3/4.4，EDS-min）

### 13.1 好友圈密钥与日志寻址

- `momentKey`（32B）：作者与好友持有，经 1:1 DR 会话分发（`{v:1,type:"circle-keys",momentKey}`，DR 会话内发送者认证，重放被 DR 拒绝）；**可重置**（换发新 key 全量重发，旧 key 无法解密新日志；不自动轮换）。
- 动态信箱：`feedId = base58(HKDF(momentKey,"mychat:moments-feed-v1:"))`——**作者日志**：动态/点赞/评论都 append 到作者日志。

### 13.2 日志条目（FeedEntry，IK 签名作者性）

`{v:1, type:"post"|"delete"|"like", cid, authorDid, contentKey?, nonce?, targetCid?, at, signature}`：

- **签名域**（确定性编码）：`"mychat:moment-entry-v1:" || type || cid || authorDid || at(8B) || targetCid有无(1B)[|| targetCid] || contentKey有无(1B)[|| contentKey || nonce]`——**所有业务字段进签名域**；signature base58。
- **传输**：`nonce(24B) || XChaCha(momentKey, nonce, JSON(entry))`——圈密钥 AEAD（非好友密文层即拒）+ IK 验签（**持有圈密钥者伪造他人条目在签名层被拒**）。
- **防重放**：接收端 cursor 增量；点赞/评论聚合幂等去重。

| type | cid | contentKey/nonce | targetCid | 语义 |
| --- | --- | --- | --- | --- |
| post | 动态内容块 CID | 内容块密钥 | — | 动态（文字+图片引用同块，图片本体另为独立 CAS 块） |
| delete | 被删动态块 CID | — | — | 墓碑 + 物理删块（`DELETE /v0/storage/blocks/:cid`）；已缓存副本无法强制删除（FR-4.4 固有边界） |
| like | "" | — | 被赞动态 cid | 点赞（append 到**作者日志**——互动事件发布到可见性集合 §7.3） |

### 13.3 时间线与聚合

本地聚合：设备对每个持有其 momentKey 的联系人增量拉取日志（cursor 治理与 §8.4 一致），post 取块解密入本地缓存、delete 应用墓碑、like/comment 聚合到目标动态；**作者对自身日志同样聚合互动条目**。排序仅按时间（无算法推荐，Non-Goals）。

### 13.4 评论（v0.2 现状）

v1 评论经 1:1 会话投递（**仅作者可见**）；好友圈共享评论（评论条目 + 内容块入作者日志，对可见性集合成员可见）为下一批次目标——**设计方向与本 §14 的互动事件模型一致**。

### 13.5 边界（如实披露）

momentKey 泄露 = 好友圈历史暴露（可重置止损，不轮换追溯）；日志信箱为公共 append，依赖条目 IK 签名保证作者性；单动态信箱 1000 条配额（开发节点属性）；SVG 图标对 iOS apple-touch 不生效（PWA 形态边界）。
