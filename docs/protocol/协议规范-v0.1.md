## 1. 密码学套件（基线，禁止自研密码学）

| 用途 | 算法 | 实现 |
| --- | --- | --- |
| 身份签名 | Ed25519 | @noble/curves |
| DH / 密钥协商 | X25519 | @noble/curves |
| KDF | HKDF-SHA-256（RFC 5869） | @noble/hashes |
| AEAD | XChaCha20-Poly1305（24B 随机 nonce） | @noble/ciphers |
| 内容哈希 / 指纹 | BLAKE3（32B 输出） | @noble/hashes |
| 文本编码 | base58btc（DID/伪地址）、小写 hex（JSON 序列化） | @scure/base |

X25519 私钥在生成与持久化时**必须 clamp 规范化**（`k[0]&=248; k[31]&=127; k[31]|=64`，RFC 7748 §5）——消除等价类，使存储完整性校验可覆盖私钥每一字节。

## 2. 身份与 DID

- 分层密钥：`IK-ed`（Ed25519，DID 本体）+ `IK-x`（X25519，X3DH 身份 DH 密钥）+ `DK-ed`（设备签名，M0 单设备）。
- `DID = "did:mychat:" || base58(IK-ed 公钥)`。自认证，无需注册机构。
- `IK-x 绑定`：`ikxBindingSig = Ed25519.Sign(IK-ed, "mychat:ikx-bind:" || IK-x 公钥)`。所有采信 IK-x 公钥的场景必须先验该绑定（防中间人替换）。
- 身份序列化（本地持久化）必须具备全字节防篡改校验：did 重算一致 + 三对密钥公私钥一致 + IK-x 绑定验签 + X25519 私钥 clamp 规范性。

## 3. 用户名记录（Registry）

```
UserNameRecord = { name, did, ktIndex, signature }
被签消息 = "mychat:name-v1:" || u16be(len(name)) || name-utf8 || did-utf8 || u64be(ktIndex)
signature = Ed25519.Sign(IK-ed, 被消息)
```

- 客户端**永远**自主验签后才采信映射（SR-5）；节点验签仅作垃圾准入。
- 用户名约束（v0.1）：`^[A-Za-z0-9_-]{1,64}$`。
- 每次注册必须锚定 KT 日志事件（type=`register`，payload=name-utf8）。

## 4. 预密钥束（PreKeyBundle）

```
PreKeyBundle = { did, ikxPublic(32B), ikxSignature, spkPublic(32B), spkSignature, spkExpiresAt, opkId, opkPublic(32B) }
spkSignature  = Ed25519.Sign(IK-ed, "mychat:spk:" || spkPublic)
ikxSignature  = 同 §2 绑定签名
opkId         = u32be(BLAKE3(opkPublic)[0:4])      // OPK 公钥指纹（防 OPK 篡改）
spkExpiresAt  = 毫秒 epoch（v0.1 有效期 ≤ 30 天）
```

- 二进制编码（251B 定长，v1）：`"MCPB" magic(4B) || version(1B=1)` + 6 个 `u16be 长度前缀` 字段（did 变长，其余定长）+ `spkExpiresAt(u64be)` + `opkId(u32be)`。解码端严格校验 magic/版本/各长度/总长/did 格式。
- 节点分发端点对 bundle 验签后仅按 DID 存"当前版本"；客户端仍须自主验签。

## 5. X3DH 握手（1:1 会话建立）

发起方 A → 响应方 B（B 的 bundle 已验证）：

```
EK_A        = 一次性 X25519 密钥对
DH1 = X25519(IK-x_A, SPK_B)   DH2 = X25519(EK_A, IK-x_B)
DH3 = X25519(EK_A, SPK_B)     DH4 = X25519(EK_A, OPK_B)
SK  = HKDF-SHA256(ikm = 0x00(32B) || DH1||DH2||DH3||DH4, salt = 0x00(32B), info = "mychat:x3dh:v1", 32B)
AD  = IK-x_A 公钥 || IK-x_B 公钥
```

- 初始消息头：`{ ikxSenderPublic, ekPublic, opkId }`（响应方据此定位 OPK；**响应方必须在接受后销毁该 OPK**）。
- 响应方镜像四组 DH 得同一 SK；SK 即 Double Ratchet 初始 root key 输入。
- 握手首条消息明文（Inner Handshake Payload，JSON UTF-8）：`{ "v": 1, "fromDid": string, "fromName": string|null, "note": string }`。

## 6. Double Ratchet（会话加密）

Signal 规范实现（`packages/core/src/signal/ratchet.ts`），要点：

- `KDF_RK(rk, dh) = HKDF(rk||dh, salt=rk, info="mychat:dr:rk:v1", 64B) → (rk', ck)`
- `KDF_CK(ck)   = HKDF(ck, salt=0x00(32B), info="mychat:dr:ck:v1", 64B) → (ck', mk)`
- 消息头 `DrHeader = { dh(32B), pn(u32be), n(u32be) }`，明文传输且并入 AEAD 关联数据：`AD_total = AD || header || nonce`。
- 每消息独立 `mk` + 24B 随机 nonce；跳过消息上限 `MAX_SKIP = 1000`；跳过 key 保存至乱序消费。
- **重放防护**：当前链内 `n < recvCount` 的消息直接拒绝（不推进链）；skipped 中 key 消费即删（第二次必败）。
- 传输格式见 §7。

## 7. 会话消息传输格式（信封 payload 内层）

```
kind = 0x01 初始消息:
  [0x01][ikxSender(32B)][ekPublic(32B)][opkId(u32be)][DrHeader(40B)][nonce(24B)][ctLen(u32be)][ct]
kind = 0x02 后续消息:
  [0x02][DrHeader(40B)][nonce(24B)][ctLen(u32be)][ct]
DrHeader = [dh(32B)][pn(u32be)][n(u32be)]
```

## 8. 信封与投递（Level0 元数据保护子集）

### 8.1 信封二进制格式

```
[version(1B)=1][epoch(u32be)][padClass(1B)][nonce(24B)][u8be 伪地址字节数][伪地址-utf8][u32be 负载长][负载]
```

- `payload = applyPadding(内层 wire)`：`[u32be 原长][wire][零填充]` 至档位定长。
- 填充四档：`256B / 1KB / 16KB / 128KB`（`padClass 0..3`，按 `wire.length+4 ≤ 档位` 选最小档）。

### 8.2 伪地址与会话信箱

```
mailboxSecret = HKDF(SK, salt=0x00(32B), info="mychat:mailbox-secret:v1", 32B)
epoch = floor(unix_ms / EPOCH_MS)，EPOCH_MS = 60_000
信箱伪地址 = base58(HKDF(mailboxSecret, salt=u64be(epoch), info="mychat:mailbox:v1:i2r"|"r2i", 18B))
方向：senderIsInitiator === sending → "i2r"，否则 "r2i"（双方视角计算结果一致）
```

伪地址每会话每 epoch 轮换；中继/存储只见伪地址（SR-2）。

### 8.3 发现信箱（新会话可达性）

```
discoveryInboxId = base58(HKDF(IK-ed 公钥, salt=0x00(32B), info="mychat:discovery:v1", 18B))
```

承载握手初始消息。**边界披露（Level0）**：发现信箱地址可被关联到 DID；会话流量不受影响。匿名化握手为 M2 增强项。

### 8.4 投递模型

- **信箱为主通道**（可靠、最终一致 NFR-5）：所有消息 append 至目标信箱，接收端按单调 cursor 增量拉取；拉取窗口须覆盖 `[now-1, now, now+1]` 三个 epoch 防轮换漏收。
- **WS 仅作唤醒**（加速）：`mailbox-activity` 通知不含内容；客户端收到后走统一拉取路径（天然去重）。
- 在线直投（`IRelay.send`）为协议保留边界，v0.1 客户端不依赖。

## 9. 节点接口（dev-node v0.1）

| 方法/路径 | 说明 |
| --- | --- |
| `POST /v0/registry/register` | 注册 `{ record }`；节点验签+重名检查 |
| `GET /v0/registry/resolve/:name` | 查询记录（404 = 不存在） |
| `PUT /v0/registry/bundle/:did` | 上传 bundle（节点验签 + DID 格式校验） |
| `GET /v0/registry/bundle/:did` | 取 bundle（404 = 不存在） |
| `POST /v0/kt/append` · `GET /v0/kt/list/:did` | KT 事件 v0（append-only） |
| `PUT/GET /v0/storage/blocks/:cid` | 加密块（CAS 幂等，≤16MB） |
| `POST /v0/storage/mailboxes/:id/append` | 投递信封（结构校验：nonce 24B、padClass 0-3、payload ≤128KB；配额 1000 条） |
| `GET /v0/storage/mailboxes/:id?cursor=N` | 增量拉取 `{ envelopes, cursor }` |
| `POST /v0/relay/send` | 在线直投（202 = 已尝试投递） |
| `WS /v0/relay/subscribe?mailbox=:id` | 唤醒订阅（`mailbox-activity` / `envelope` 直投） |

### 9.5 唤醒网关（M1 定稿，FR-5.6 的 Level0 形态）

- **语义**：网关只承载"某伪地址信箱有新内容"的布尔信号（`mailbox-activity`），**永不承载内容**——内容一律走信箱拉取路径（§8.4）。
- **信号可关联性边界（Level0 如实披露）**：WS 长连接的 IP/时序可被网关观察者关联到伪地址（伪地址每 epoch 轮换缓解跨期关联）；信号与 DID 的最终解耦（sealed sender 化网关、真实 Web Push/VAPID 令牌池与轮换）为 M2。
- **浏览器通知（M1）**：客户端在页面隐藏时以 Notification API 呈现摘要（内容不出本机）；页面关闭即无通知通道（W2），推送网关的常驻形态 M2。

线格式：信封二进制字段 base64 的 JSON。节点可信边界：只搬运密文、只做结构与签名准入（见产品设计报告 §2.3）。

## 10. 安全考量与边界（v0.1 如实披露）

| 项 | 状态 |
| --- | --- |
| 内容机密性（SR-1） | 全程 E2EE；节点无明文路径 |
| 关系机密性（SR-2） | 会话流量伪地址轮换；**发现信箱与 DID 可关联**（§8.3），时序分析抗性有限（Level0） |
| 重放/篡改/伪造（SR-4） | AEAD + header 绑定 + 链内重放拒绝 + skipped 消费即删 |
| 映射可验证（SR-5） | 双端验签 + KT v0（append-only）；Merkle 证明 M1 |
| Web 端密钥存储（W1） | IndexedDB 无系统级保护；口令加密与社交恢复 M1 |
| OPK 单发 | M0 单 OPK：并发握手可能失败（后到者拒），重新添加即可；OPK 池 M1 |

## 12. 版本与演进

- 信封/wire/bundle 均带版本字段；客户端维护 ≥2 个版本兼容窗口（NFR-10）。
- v0.2 预告：多 OPK 池与轮换、送达/已读回执、KT Merkle 证明、富媒体消息（EDS 块引用）、SPK 轮换。
