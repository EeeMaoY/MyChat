## 3. 关键设计约定（S9）

1. **OPK 池（服务端组装）**：`PreKeyBundle` wire 结构不变（协议规范 §4 不升版）；节点 `GET /v0/registry/bundle/:did` 从该用户池中挑一个未消耗 OPK 组装返回，**返回即标记已发**；响应方 accept 成功后 `DELETE .../opk/:opkId` 确认消耗（未确认的由客户端对账时回收）。池空时 bundle 无 OPK 字段——v0.2 协议规范将标注 opkOptional（core X3DH 的 DH4 可选支持排期 S9 末评估，先以"池水位告警"退化）。
2. **会话替换语义**：Double Ratchet 会话与 (contact, 创建时间) 绑定；新握手 accept 成功即替换，旧会话丢弃（消息历史不动）。替换事件上抛 UI（对齐设计报告 §10.3"联系人设备变更轻提示"）。
3. **包裹 v2**：`{ v:2, identity, myName }`；恢复导入后自动 `setUsername` 尝试重注册原用户名（被占用则提示）。
4. **cursor 分类**：解密/解析失败 → cursor 照常推进（安全丢弃，SR-4 语义）；kv 写入失败 → 不推进（下轮重试）。空拉取仅更新内存。

## 4. S9 验收 Gate

1. 恢复后（原数据已清）与旧联系人**重新握手即可双向通信**（KI-1/KI-4 闭环，浏览器 e2e）。
2. 同一联系人连续两次"更换设备"（重握手）后，双方会话均可用且消息历史保留。
3. 恢复完成后用户名自动回填（或明确提示占用），托管副本引导出现（KI-2）。
4. 长时间运行 cursor 键数量与活跃信箱数同阶（KI-3）。
5. 恢复演练：一键完成本地完整性检查并给出可理解报告（UX-2）。
6. 回归：M0/M1 全部既有测试保持绿色。

## 5. S10 设计约定与验收记录（v1.1 增补）

### 5.1 关键设计（协议细节见协议规范 §9.6）

1. **设备凭证（DK cert）**：IK 签名 `{did, dkId, label, issuedAt, expiresAt}`（默认 90 天，临期 7 天自动续签）；登记锚定 KT `device-add`，吊销（IK 签名声明）锚定 KT `device-revoke` 并**立即停发**该设备的 bundle/OPK 池。
2. **按设备分槽分发**：bundle 模板与 OPK 池按 `(did, dkId)` 存储；分发在有效设备集内确定性 round-robin（多设备自然负载均衡）；写操作须指向有效设备（403 = 未登记/已吊销/已过期）。
3. **对端会话轮换**：无推送信令——发送路径节流（每联系人 60s）拉对方 KT 事件流，本地折叠 + 逐事件验签（SR-5 不采信节点视图），有效设备集指纹变化即自动重握手（S9 替换语义，历史保留 + UI 轻提示）。
4. **诚实边界（协议规范 §9.6 同步披露）**：当前每台设备持有 IK 副本（Level0），DK 为设备生命周期凭证；"DK 作实际加密操作者（SPK 由 DK 签、IK 不落端）"需 bundle wire v2，排期后续里程碑。多设备不互相同步会话历史；吊销不远程擦除被吊销设备本地历史。

### 5.2 S10 验收 Gate（Node e2e，全部通过；全仓 135 项测试绿）

1. 双设备 round-robin：连续取 bundle 交替命中两台设备，两位联系人各自握手后双向通信可用。
2. 吊销停发：吊销设备 A 后 KT 折叠指纹变化可核验，重新握手必然落在存活设备 B，消息照常收发；伪造吊销被拒（server.test）。
3. 全部设备吊销 → bundle 分发 404；被吊销设备再上传材料 403（停发完整性）。
4. 客户端：设备管理 UI（本设备信息/列表/两段确认吊销）、导入备份即新设备入网、凭证临期自动续签。
5. 回归：M0/M1/S9 全部既有测试保持绿色（core 113 + dev-node 22）。

### 5.3 S10 过程记录

- 修复 S9-⑦ 遗留 bug：恢复演练公告签名校验编码不一致（base64 写入/base58 读取），检查恒失败（0d642bb）。
- 分槽分发实现中发现 `perDevice` 层级错位缺陷（issued 标记失效被 catch 吞掉），以最小复现脚本定位后重写为三层 get-or-create（`deviceSlot`）——分发一次性语义恢复。
