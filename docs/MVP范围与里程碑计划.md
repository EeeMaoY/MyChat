## 1. 范围调整说明

产品设计报告（v1.1）的基线是"三平台客户端（iOS/Android/桌面）+ 8–10 人 + 8 个月"。根据发起人决策，项目初期目标调整为**可交付的 Web 客户端**：先以单一 Web 端完整验证产品核心命题（E2EE + 元数据保护 + 数据所有权），再扩展到其他平台。需求基线（需求分析报告 v1.1）**不变**，本计划仅调整交付顺序与实现载体，并按 Web 平台特性补充约束。

### 1.1 已确认的关键决策（2026-10-31）

| # | 决策 | 对应 ADR |
| --- | --- | --- |
| D1 | Web 客户端密码学层采用**全 TypeScript**（不采用 Rust→WASM） | ADR-9（修订 ADR-6） |
| D2 | **MVP 不做群组**；MLS 移入 M2 评估 | ADR-10（收窄 ADR-2 适用范围） |
| D3 | 服务域 MVP 以**单体 dev-node** 落地，四类协议接口第一天即分离 | ADR-11 |
| D4 | M0 功能主线 = **IM（1:1 E2EE 全链路）**，动态/群组随后迭代 | ADR-12 |

## 2. 决策记录增补（ADR-9 ~ ADR-12）

### ADR-9：Web 客户端采用全 TypeScript 实现（修订 ADR-6 在 Web 范围的适用性）

- **备选**：Rust core → WASM（原 ADR-6）；TS UI + 现成 WASM 密码库绑定。
- **选择**：全 TypeScript。密码**原语**使用经审计的 `@noble` 系列（`@noble/curves` X25519/Ed25519、`@noble/ciphers` AEAD、`@noble/hashes` BLAKE3/HKDF）；协议**逻辑**（X3DH、Double Ratchet、信封、EDS）按协议规范自实现，辅以测试向量与已知答案测试。
- **理由**：MVP 交付速度最优；工具链单一；同构代码可同时跑在浏览器与 dev-node。
- **代价/技术债**：未来移动端若回归 Rust core，协议层需要重写。缓解：协议规范 + 测试向量先行，保证重写时可等价替换；`packages/core` 的协议状态机保持纯函数化、平台无关。

### ADR-10：MVP 阶段不做群组，MLS 移入 M2

- **理由**：群组加密是需求中复杂度最高的密码学面（ADR-2 的 MLS 依赖额外集成成本）。先以 1:1 会话完整验证「X3DH + Double Ratchet + 匿名投递 + 离线信箱」核心链路，降低并行风险。
- **代价**：FR-6.x（P0）延后满足，MVP 不宣称覆盖群组场景。

### ADR-11：服务域 MVP 以单体 dev-node 落地，协议接口分离

- **选择**：一个进程实现 Relay / Storage / Registry / KT Log 四类角色，但四类接口在协议层**第一天即独立定义与版本化**；任何第三方可按接口独立实现并部署自己的节点。
- **理由**：Web 客户端演示需要真实可跑的节点；单体形态开发联调成本最低。去中心化的诚意由"接口分离 + 多主体可实现"保证，而非部署拓扑。
- **代价**：M0 阶段网络拓扑是单点（开发环境属性，如实标注）；生产多节点部署策略延后设计。

### ADR-12：M0 功能主线 = IM（1:1 E2EE）

- **理由**：IM 主线（在线直投 + 离线信箱）以最短路径验证产品核心命题：内容保密性（SR-1）、关系机密性（SR-2）与即时性（G4）。动态/时间线（FR-4.x）依赖 EDS 与图谱加密的完整形态，放后续迭代。
- **代价**：早期演示偏"IM"而非"社交网络"，动态主线在 M1 末评估启动。

## 3. Web 平台约束与对策（对需求文档的补充）

| # | Web 平台约束 | 对策 | 需求影响 |
| --- | --- | --- | --- |
| W1 | 长期密钥仅能存于 IndexedDB/OPFS，无系统 keychain/安全元件，设备丢失防护弱于原生端 | 私有区数据以设备口令派生密钥加密存放；社交恢复（FR-1.3）提前至 M1；产品如实披露（P7/UX-7） | 威胁模型 7.1 增补："Web 端设备窃取者"防护降级声明 |
| W2 | 浏览器无常驻后台进程，页面关闭即离线 | M0：在线接收依赖页面存活（WebSocket 直投）+ 上线时拉取离线信箱；Web Push 网关（仅唤醒令牌，FR-5.6 设计一致）M1 立项 | FR-5.1/5.6 的 Web 端实现边界 |
| W3 | 浏览器可在存储压力下驱逐 IndexedDB 数据 | 存储访问统一走抽象接口；托管加密副本（FR-7.3）提前至 M1 | FR-7.1 的 Web 端风险 |

| W5 | Web Push 必须经中转服务器 | 自建 push gateway，仅承载轮换唤醒令牌，与 FR-5.6/R7 设计一致 | 无新增冲突 |

## 5. 系统结构与模块划分

### 5.1 Monorepo 结构（npm workspaces）

```
MyChat/
├── docs/
│   ├── 需求分析报告.md            # 基线（不变）
│   ├── 产品设计报告.md            # 基线（ADR 增补）
│   ├── MVP范围与里程碑计划.md      # 本文档
│   └── protocol/                  # 协议规范 v0.1（S4 定稿）
└── packages/
    ├── core/                      # 协议与密码学核心（纯 TS、浏览器/Node 同构）
    │   └── src/
    │       ├── crypto/            # @noble 原语封装（X25519/Ed25519/HKDF/AEAD/BLAKE3）
    │       ├── identity/          # IK/DK/DID/用户名签名记录
    │       ├── signal/            # X3DH + Double Ratchet 状态机
    │       ├── envelope/          # 信封编解码（伪地址/填充/时间桶/版本）
    │       ├── eds/               # 加密数据空间（M0：本地块 + 信箱写入/取回）
    │       ├── store/             # 持久化接口（IndexedDB / 内存实现）
    │       └── protocol/          # 服务域四接口类型（IRelay/IStorage/IRegistry/IKTLog）
    ├── dev-node/                  # 单体 dev 节点（实现 core/protocol 四接口）
    └── client-web/                # React + Vite Web 客户端
```

依赖方向：`client-web → core ← dev-node`；client 与 node 之间**只经协议通信**（信封 + 四接口），无其他耦合。

### 5.2 服务域四接口（M0 冻结 v0.1）

| 接口 | 职责 | 关键方法（概念） |
| --- | --- | --- |
| `IRelay` | 在线密文包投递 | `subscribe(mailboxId)` / `send(envelope)` |
| `IStorage` | 信箱与加密块存储 | `putBlock` / `getBlock` / `mailboxAppend` / `mailboxFetch` |
| `IRegistry` | 用户名 → DID 映射 | `register(nameRecord)` / `resolve(name)` |
| `IKTLog` | 映射变更事件日志（v0：append-only） | `append(event)` / `list(did)` |

## 8. M0 验收 Gate

1. **功能**：两个隔离浏览器环境完成「身份创建 → 用户名注册 → 扫码加好友 → 互发 E2EE 消息 → 一方离线留言 → 上线收取」全旅程。
2. **安全**：
   - dev-node 落盘数据中无可识别的用户内容明文（自动化明文扫描）；
   - 信封不含收发双方 DID 明文（仅伪地址）；同信封重放被接收端拒绝；
   - Registry 记录无 IK 签名即无效（客户端拒收未签名映射）。
3. **协议**：X3DH/Double Ratchet 具备测试向量与已知答案测试；协议规范 v0.1 入库 `docs/protocol/`。
4. **体验**：全新环境到发出第一条 E2EE 消息 ≤ 3 分钟，0 次密钥相关操作。
5. **工程**：monorepo 一键构建与测试通过；core 密码学模块具备单元测试覆盖。

## 9. 风险登记（Web-first 增量）

| # | 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- | --- |
| TR-1 | 自实现 Signal 协议存在正确性缺陷 | 中 | 高 | 测试向量 + 已知答案测试；协议状态机与原语分层，保留切换成熟实现（如 libsignal WASM）的接口余地 |
| TR-2 | Web 端密钥存储防护弱于原生（W1） | 确定 | 中 | 如实披露；社交恢复提前至 M1；口令加密私有区 |
| TR-3 | 浏览器驱逐 IndexedDB 导致本地数据丢失（W3） | 低 | 高 | 托管加密副本提前至 M1；关键操作前容量检测 |
| TR-4 | WebSocket 直连暴露 IP 与时序元数据（Level0 固有边界，同设计报告 Q1） | 确定 | 中 | 如实分级披露；M2 评估增强模式 |
| TR-5 | dev-node 单点被误当"生产形态"理解 | 低 | 中 | 文档与产品界面明示开发环境属性；接口分离保证可替换 |
