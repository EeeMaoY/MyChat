## 1. 背景

M2 第一阶段（S9 恢复闭环 / S10 多设备）已交付并推送（`31b14e3`），全仓 135 项测试绿，**初期目标（可交付的 Web 客户端）已超额完成**。本文档对 M2 第二阶段候选事项逐一评估并给出 M3 范围建议，供范围决策后开工。

候选池（M2 计划 v1.0 §1 登记）：① 群组（ADR-10 评估点）② 动态+时间线（ADR-12 评估点）③ Level1 增强元数据 ④ WoT 反滥用 ⑤ KT 一致性证明与多副本。

## 2. 候选一：群组（FR-6.1/6.2 P0，ADR-10 评估点）

里程碑表预告了两条落地路线，评估后补充第三条务实路线：

### 2.1 选项对比

| 选项 | 内容 | 优点 | 代价与风险 | 结论 |
| --- | --- | --- | --- | --- |
| A：OpenMLS WASM 绑定 | Rust 审计实现编译 WASM，TS 绑定层自写 | 密码学正确性由审计库保证（TR-1 纪律的最佳满足） | Rust 工具链进入 monorepo（构建复杂度陡增）；无维护中的官方 JS 绑定，**绑定层本身不在审计范围**（集成 bug 高发区）；与既有 wire/信封/存储的适配面全新 | 推迟（触发条件见 §6） |
| B：纯 TS 自实现 MLS | TreeKEM/KeySchedule/Exporter 全自研 | 无 | **直接违反 TR-1（不自研密码学）红线**，TreeKEM 密码学面是既有全部工作的数倍 | 否决 |
| C：简化 Sender-Keys（1:1 扇出过渡） | 每发送方一个群链密钥（CK），经既有 1:1 DR 会话分发一次；群消息用该 CK 加密一次、信箱扇出 N 份 | **零新密码学原语**（CK 分发走既有会话/ECIES）；复用全部既有基础设施（信箱/信封/DR/OPK 池/多设备）；FR-6.1/6.2 可满足；N≤50 线性开销可接受 | FR-6.3 大群组（500+）不满足；组内前向保密弱于 MLS（成员变更需全量重分发 CK）——如实标注 | **建议 M3 采纳** |

### 2.2 选项 C 设计要点（概要）

1. **群组状态**：群主维护权威清单（members/policy/epoch），变更经群控会话同步；v1 权限收敛为 owner/admin/member 三级（FR-6.4 完整角色表 P1）。
2. **密钥模型（Sender-Keys）**：epoch 内每发送方持有自己的链密钥（复用 DR 的 KDF_CK 思想做组内前向推进）；**成员加入/移除 → epoch+1 → 存活成员链密钥全量重分发**（移除者拿不到新 CK = FR-6.2 断读；被移除者无法伪造——群消息带发送方签名）。
3. **服务域零改动**：群消息就是普通信封投各成员信箱；大附件走既有 CAS 块（一次上传、CID 扇出）。
4. **诚实边界**：50 人上限 v1 硬编码；"群元数据对基础设施不可见"（FR-6.1）由"清单密文 + 信箱伪地址"达成 Level0 形态，群成员列表对节点不可见但扇出模式可被流量分析观察（与 1:1 同级披露）。

### 2.3 工作量估算（一个 sprint，S11）

core `groups` 模块（epoch/CK 分发/组内加密/成员变更语义）+ 单测 → client 群组 UI（建群/邀请/退群/群聊复用 ChatPanel）→ Node e2e（建群 → 群聊 → 移除成员断读 → epoch 重分发）。预估与 S10 同量级（含 Gate 回归）。

## 3. 候选二：动态+时间线（FR-4.1/4.2/4.4 P0，ADR-12 评估点）

### 3.1 范围裁剪：EDS-min，不做完整 EDS

设计报告 §6.1 的完整 EDS（区密钥分级/托管复制/删除墓碑）范围过大。动态 v1 只需 **EDS-min**：

- 作者维护 append-only **动态日志**（块序列，CID 链 + 内层签名，CAS 存储——既有块存储直接复用）；
- 内容密钥 CK 按可见性集合包裹：**好友圈 = 单一 CK 经 1:1 会话分发给全部好友**（与群组 Sender-Keys 的分发机制**同构**）；指定联系人 = 逐一会话包裹（既有 ECIES）。

**关键洞察**：好友圈动态 ≈ 一个"动态发布者管理的单管理员群"。**先做候选一（群组）的密钥分发层，候选二直接复用**——两件事的排序由此确定。

### 3.2 功能切分（v1）

| FR | v1 形态 | 说明 |
| --- | --- | --- |
| FR-4.1 发布 | 文字 + 图片（复用附件加密块） | 视频/链接预览 P1 |
| FR-4.2 时间线 | 本地聚合关注集合的日志增量 | 本地缓存离线可刷（§7.4 设计如实落地） |
| FR-4.3 互动 | v1 仅评论（经可见性集合会话投递） | 点赞聚合、转发 P1 |
| FR-4.4 删除 | 能力吊销 + 删除通知（新读者不可见） | **物理不可强制删除已缓存副本——需求文档固有边界，UI 如实告知** |
| FR-4.5 公开内容 | 不做（P1，触发条件：产品需要公开影响力信号） | |

### 3.3 工作量估算（一个 sprint，S12）

core `eds` 模块（日志块/能力包裹/墓碑）+ client（发布流/时间线页/增量同步）+ e2e（发布 → 好友拉取 → 删除后新读者不可见）。

## 4. 候选三~五评估（建议 M3 暂缓或捎带）

| 候选 | 现状与价值 | 建议 |
| --- | --- | --- |
| ③ Level1 增强元数据 | sealed sender/时间桶增强依赖**真实多节点拓扑与流量形态**才有意义；当前单 dev-node 环境收益接近零 | M4+（与多节点部署同批） |
| ④ WoT 反滥用 | 依赖真实用户规模与滥用样本；M3 无此输入 | M4+（先在 UI 落地"信任标注"的最小形态可提前） |
| ⑤ KT 一致性证明 | RFC 6962 一致性证明端点 + 客户端核验，core 已有 Merkle 基础，**工作量最小（1-2 天）**，是 SR-5 的最后一块 | **M3 捎带项**；多副本延后（依赖多节点） |

| Sprint | 内容 | 对应需求 |

## 6. 风险与开放问题

1. **Sender-Keys 的安全边界**：组内前向保密依赖 epoch 重分发频率；无 MLS 树结构的 O(log n) 成员变更开销。若产品要求 >50 人群或更高安全档，触发 OpenMLS WASM 立项（选项 A，届时一并评估 Rust 工具链引入）。
2. **信箱配额**：扇出 N 份群密文受单信箱 1000 条配额约束（开发节点属性）；群消息大附件走 CAS 不受影响。50 人群纯文本场景配额充裕，e2e 中验证。
3. **动态的同步节奏**：关注集合的日志增量拉取在多关注对象下的轮询压力，S12 设计期定量评估（必要时引入 §9.5 唤醒网关的信箱批量订阅扩展）。
4. **MLS 生态跟踪**：openmls（Rust）与 wire 系 TS 实现的成熟度每季度复查一次，不作为 M3 依赖。
